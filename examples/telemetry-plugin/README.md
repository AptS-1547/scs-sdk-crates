# SCS SDK Telemetry Example

[中文](README.zh.md) | **English**

This crate is the primary real-game example for `scs-sdk-crates`. It builds a
native SCS telemetry plugin while keeping all handwritten application code on
the safe Rust side of the framework boundary.

It is both:

- a readable example of implementing `TelemetryPlugin`; and
- an end-to-end fixture exercised against a real Euro Truck Simulator 2
  process.

It is not an ETS2 Dispatch product plugin. Networking, web applications,
task dispatch, persistence, save-game parsing, and other product behavior
belong in separate repositories.

## What the example demonstrates

The plugin uses only the public `scs-sdk-plugin` API and its typed `sdk`
re-export. Application code explicitly:

1. declares plugin metadata and compatibility requirements;
2. subscribes to each required event and channel during initialization;
3. receives typed channel updates and builds a latest-value snapshot;
4. handles lifecycle, configuration, and gameplay events;
5. writes bounded diagnostic output through the game's logging callback; and
6. resets product state during initialization and shutdown.

Exported SCS entry points are generated by:

```rust
export_plugin!(TelemetryExample::default());
```

The application does not declare an ABI function, inspect a raw pointer, use a
C string, or call `scs-sdk-sys` directly.

## Compatibility contract

The example requires:

| Domain | Minimum | Reason |
| --- | ---: | --- |
| Telemetry API | 1.01 | Gameplay events and signed 64-bit gameplay values require API 1.01. |
| ETS2 telemetry schema | 1.14 | SCS introduced the gameplay-event descriptors in this game schema. |
| Game | Euro Truck Simulator 2 | The example's compatibility declaration currently lists ETS2 explicitly. |

Telemetry API version, game telemetry schema, and public game version are
separate version domains. A real startup log may therefore contain values such
as:

```text
game_display_name="Euro Truck Simulator 2 1.60.1.7s"
telemetry_api=1.1
telemetry_schema=1.19
```

## Explicit subscriptions

### Event classes

The example registers all six telemetry event classes explicitly:

| Event | Example use |
| --- | --- |
| `FrameStart` | Capture the real-time render timestamp and detect timer restarts. |
| `FrameEnd` | Emit a rate-limited snapshot after the frame's updates. |
| `Paused` | Stop driving snapshots while telemetry is paused. |
| `Started` | Resume driving snapshots when telemetry starts. |
| `Configuration` | Decode and log the active job configuration. |
| `Gameplay` | Decode all six gameplay event payload shapes from SDK 1.14. |

The initialized framework line should report:

```text
events=6
```

### Channels

The example registers eight scalar channels:

| Channel | SDK unit/value | Example use |
| --- | --- | --- |
| `truck.world.placement` | placement | World position and heading. |
| `truck.speed` | metres per second | Displayed as kilometres per hour. |
| `truck.engine.rpm` | revolutions per minute | Engine-state probe. |
| `truck.engine.gear` | signed integer | Current engine gear. |
| `truck.navigation.distance` | metres | Remaining route distance, displayed in kilometres. |
| `truck.navigation.time` | seconds | Remaining navigation time. |
| `truck.navigation.speed.limit` | metres per second | Current navigation speed limit, displayed in kilometres per hour. |
| `job.cargo.damage` | ratio | Latest cargo-damage value. |

The initialized framework line should report:

```text
channels=8
```

Channel callbacks are independent. `FrameEnd` reads the most recent value of
each field; the example does not assume that SCS invokes channel callbacks in a
particular order inside a frame.

## Logged behavior

### Snapshot probe

While telemetry is active, the example emits at most one snapshot per second:

```text
[scs-sdk-example] probe speed=85.3km/h rpm=1485 gear=16 \
position=(27077.895,2.983,-8572.040) heading=0.7134 \
navigation_distance=705.64km navigation_time=39887s \
speed_limit=80.0km/h cargo_damage=0.000
```

The stored SDK speed is not modified. Only the displayed value normalizes a
very small signed floating-point zero to avoid noisy `-0.0km/h` output.

### Job configuration

An active job log includes both display names and stable IDs where SCS provides
them:

```text
[scs-sdk-example] job cargo=Cars cargo_id=cars_fr mass=9010kg \
source=Amsterdam(amsterdam)/TDC Auto Terminal(tdc_auto) \
destination=Panevezys(panevezys)/BHV(bhv) \
market_raw=freight_market market_known=Some(FreightMarket) \
income=69663 planned_distance=1614km delivery_time=110550 \
cargo_loaded=true special_job=false
```

Known enum-like values and their raw SDK strings are deliberately retained
together. A future additive value remains diagnosable even when the current
typed catalog does not recognize it.

### Gameplay events

The example handles every gameplay event defined by the SDK 1.14 header:

| SDK event | Example marker |
| --- | --- |
| `job.delivered` | `[scs-sdk-example] job delivered ...` |
| `job.cancelled` | `[scs-sdk-example] job cancelled ...` |
| `player.fined` | `[scs-sdk-example] player fined ...` |
| `player.tollgate.paid` | `[scs-sdk-example] tollgate paid ...` |
| `player.use.ferry` | `[scs-sdk-example] ferry used ...` |
| `player.use.train` | `[scs-sdk-example] train used ...` |

A real ETS2 tollgate validation produced:

```text
[tollgate] Activated 'end' tollgate
[scs-sdk-example] tollgate paid amount=79
```

That sequence proves delivery and typed signed-64-bit decoding of the
`pay.amount` gameplay attribute, rather than merely proving that the generic
gameplay event class was registered.

## Safe application boundary

From the repository root, run:

```bash
scripts/check-plugin-boundary.sh examples/telemetry-plugin
```

The audit rejects handwritten application source containing raw ABI access,
including `unsafe`, raw pointers, external ABI declarations, C string types,
direct `scs-sdk-sys` access, or use of the macro-only
`scs_sdk_plugin::__private` module.

Necessary foreign-boundary code remains contained and audited in the lower
framework, wrapper, and sys crates.

## Build and verify

Run all commands from the repository root.

### Windows x86-64

```bash
scripts/build-windows-plugin.sh
```

Artifact:

```text
target/x86_64-pc-windows-gnu/release/scs_sdk_telemetry_example.dll
```

### Linux x86-64, glibc 2.17 baseline

```bash
scripts/build-linux-plugin.sh
```

Artifact:

```text
target/x86_64-unknown-linux-gnu/release/libscs_sdk_telemetry_example.so
```

### macOS x86-64

```bash
scripts/build-macos-plugin.sh
```

Artifact:

```text
target/x86_64-apple-darwin/release/libscs_sdk_telemetry_example.dylib
```

The macOS target remains x86-64 even on Apple Silicon because the current ETS2
executable and plugin process run through Rosetta. The repository scripts verify
the native file format, x86-64 architecture, and exact loader-visible exports.
The macOS build also applies and verifies an ad-hoc signature for local use.

## Install on macOS

Exit ETS2 completely, then run:

```bash
scripts/install-macos-plugin.sh
```

The installer:

1. works on a private copy of the build artifact;
2. removes quarantine from that copy when present;
3. applies an ad-hoc signature;
4. verifies Mach-O format, x86-64 architecture, signature, and exports;
5. copies the verified artifact into the ETS2 application bundle;
6. verifies the installed destination; and
7. removes only the exact fallback and legacy example filenames.

The normal and fallback examples are mutually exclusive E2E probes. To switch
to the loader fallback test, use the separate instructions in
[`../telemetry-fallback-plugin/README.md`](../telemetry-fallback-plugin/README.md).

## Real ETS2 validation

The live log is:

```text
~/Library/Application Support/Euro Truck Simulator 2/game.log.txt
```

On startup, confirm:

```text
loading 'libscs_sdk_telemetry_example'
[scs-sdk-plugin] starting plugin name="SCS SDK Telemetry Example" ...
[scs-sdk-plugin] detected ... telemetry_api=1.1 telemetry_schema=...
[scs-sdk-plugin] initialized ... events=6 channels=8
```

Enter the driving scene and exercise the behavior relevant to the test: start
and pause telemetry, accept or load a job, pass a tollgate, receive a fine, or
use a ferry/train. On final game exit, confirm:

```text
[scs-sdk-example] example state shutdown
[scs-sdk-plugin] shutdown complete plugin name="SCS SDK Telemetry Example" ...
unloaded 'libscs_sdk_telemetry_example'
```

ETS2 rewrites `game.log.txt` on every process start. Copy a log promptly when it
must become durable E2E evidence.

## Development checks

At minimum, run:

```bash
cargo fmt --all -- --check
scripts/check-plugin-boundary.sh examples/telemetry-plugin
cargo test --locked -p scs-sdk-telemetry-example
cargo clippy --locked -p scs-sdk-telemetry-example --all-targets -- -D warnings
scripts/check-plugin-macro-fixtures.sh
```

Changes affecting plugin behavior or exports should also run the applicable
platform build-and-verification scripts listed above.
