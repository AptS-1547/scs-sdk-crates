# SCS SDK Semantical Input Example

[中文](README.zh.md) | **English**

This crate is the isolated safe-Rust fixture for the SCS Input API 1.00
semantical device class. It builds a real native plugin for Euro Truck
Simulator 2 or American Truck Simulator while keeping handwritten application
code free of raw pointers, C strings, external ABI declarations, and `unsafe`.

The fixture follows the official SDK 1.14 `input_semantical` example: it
registers one bool input named `light`. SCS maps that name directly to the
game's `semantical.light?0` mix, so the plugin works without a controller
binding step.

This crate exists separately from `examples/input-plugin`. The generic example
proves user-bindable bool and normalized float inputs; this example proves
direct semantical mix routing. Keeping separate native artifacts makes the
real-game result attributable to one device class.

## Public contract demonstrated

The example depends only on `scs-sdk-plugin` and implements `InputPlugin`.
Application code explicitly:

1. declares metadata and Input API compatibility;
2. registers one semantical device during initialization;
3. declares the exact `light` bool input;
4. opts into activity notifications;
5. responds to SCS's per-frame event polling;
6. returns `None` after the one event in each sequence; and
7. resets its state during shutdown.

The loader entry points are generated by the safe macro invocation:

```rust
scs_sdk_plugin::export_input_plugin!(Plugin::default());
```

The finished dynamic library exposes exactly:

```text
scs_input_init
scs_input_shutdown
```

## Why the input is named `light`

The official SDK sample registers:

```text
device type: semantical
input name: light
value type: bool
```

The SDK documentation states that a semantical input name maps directly to a
game mix with the same name. A fresh ETS2 controls file contains an expression
equivalent to:

```text
mix light `keyboard.l?0 | semantical.light?0`
```

On macOS the active profile file is normally named `controls_osx.sii`; Windows
and Linux commonly use `controls.sii`. The filename is platform-specific, but
the `semantical.light?0` contract is the same.

Semantical devices do not appear as normal bindable controller inputs. That is
intentional: the game consumes `light` directly, and changing game mix names
would require a plugin update rather than a user binding change.

## Deterministic behavior

The official C++ sample toggles from wall-clock time. This fixture instead
toggles every 60 input frames so tests and logs are reproducible:

| Index | Mix name | Display name | Value type | Behavior |
| ---: | --- | --- | --- | --- |
| 0 | `light` | `Lights` | `Bool` | Starts `false`, becomes `true` after 60 input frames, and continues toggling every 60 frames. |

For every request marked `first_in_frame`, the fixture advances its state and
resets the device-local event cursor. It returns the `light` event once, then
returns `None`; the framework maps `None` to the SDK's `NotFound` result that
terminates the current sequence.

Logs are deliberately bounded. Each activation records the first observed
`false`, the first observed `true`, and one exhaustion marker. Later frames
continue to drive the light mix without flooding `game.log.txt`.

## Compatibility contract

| Domain | Requirement |
| --- | --- |
| Input API | Exactly 1.00 |
| ETS2 Input game version | 1.00 or a later compatible minor in major 1 |
| ATS Input game version | 1.00 or a later compatible minor in major 1 |
| Plugin architectures | Windows, Linux, and macOS x86-64 |

Input API versions and per-game Input versions remain independent from
Telemetry API versions, Telemetry schema versions, and public game versions.

## Safe application boundary

```bash
scripts/check-plugin-boundary.sh examples/input-semantical-plugin
```

The source uses `#![forbid(unsafe_code)]`. The boundary audit also rejects raw
pointers, handwritten ABI functions, C string types, direct `scs-sdk-sys`
access, and framework-private macro support paths. FFI, panic containment,
callback ownership, and SDK result conversion stay inside the audited crates.

## Build and verify

Run commands from the repository root. Each script builds a release dynamic
library and verifies its native format, x86-64 architecture, and exact two
Input exports. The Linux build retains the glibc 2.17 floor; the macOS build is
ad-hoc signed and signature-verified.

| Platform | Command | Artifact |
| --- | --- | --- |
| Windows x86-64 | `scripts/build-windows-input-semantical-plugin.sh` | `target/x86_64-pc-windows-gnu/release/scs_sdk_input_semantical_example.dll` |
| Linux x86-64 | `scripts/build-linux-input-semantical-plugin.sh` | `target/x86_64-unknown-linux-gnu/release/libscs_sdk_input_semantical_example.so` |
| macOS x86-64 | `scripts/build-macos-input-semantical-plugin.sh` | `target/x86_64-apple-darwin/release/libscs_sdk_input_semantical_example.dylib` |

The macOS artifact remains x86-64 on Apple Silicon because the current SCS game
plugin process runs through Rosetta.

## Install and exercise on macOS

Exit ETS2 completely, then run:

```bash
scripts/build-macos-input-semantical-plugin.sh
scripts/install-macos-input-semantical-plugin.sh
```

The installer works from a private copy, clears quarantine, applies an ad-hoc
signature, verifies the two exports, writes the selected dylib, verifies the
installed bytes, and only then removes the exact generic Input fixture filename.
It leaves Telemetry libraries and unrelated plugins untouched.

The generic and semantical Input examples are mutually exclusive real-game
fixtures because both export `scs_input_init` and `scs_input_shutdown`. Use the
generic installer to switch back; do not keep renamed duplicate Input libraries
beside either artifact.

No binding UI action is required. Start the game, enter a state where vehicle
lights are visible, and wait for the semantical device to toggle the `light`
mix. The live macOS log is:

```text
~/Library/Application Support/Euro Truck Simulator 2/game.log.txt
```

Expected startup and callback evidence:

```text
[scs-sdk-plugin/input] starting plugin name="SCS SDK Semantical Input Example" ...
[scs-sdk-plugin/input] detected ... input_api=1.0 input_game_version=1.0
[scs-sdk-input-semantical-example] registered device_type=semantical inputs=1 mix=light value_type=bool ...
[scs-sdk-input-semantical-example] device active=true
[scs-sdk-input-semantical-example] first poll after activation
[scs-sdk-input-semantical-example] emitted index=0 mix=light type=bool value=false
[scs-sdk-input-semantical-example] event sequence exhausted
[scs-sdk-input-semantical-example] emitted index=0 mix=light type=bool value=true
```

On exit, confirm framework shutdown and library unload:

```text
[scs-sdk-input-semantical-example] shutdown
[scs-sdk-plugin/input] shutdown complete plugin name="SCS SDK Semantical Input Example" ...
unloaded 'libscs_sdk_input_semantical_example'
```

A complete real-game E2E record includes load, version detection, semantical
registration, automatic activation, both bool states, exhaustion, visible light
behavior, shutdown, and unload from one run.

## Confirmed ETS2 E2E

The macOS x86-64 artifact was exercised in Euro Truck Simulator 2 `1.60.1.7s`
on 2026-07-26. The game loaded the library, negotiated Input API 1.00 and Input
game version 1.00, registered the one-input semantical device, activated it
without a binding step, consumed both `false` and `true`, reached the
`NotFound` sequence boundary, and completed clean shutdown and unload.

The visible vehicle lights automatically cycled while the fixture was active.
The preserved local log is:

```text
tmp/input-e2e-semantical-light-2026-07-26-final.log.txt
SHA-256: 0b83347bdbf015520edd1ef4646cf3db15f409d3bd1cccf1282051f79b1f55b1
```

This result proves the real semantical routing path, not merely device
registration or callback compilation. Errors elsewhere in that game session
came from the intentionally rejecting Telemetry fallback fixture and installed
mods; no Semantical Input runtime error, panic, deadlock, or crash was present.
