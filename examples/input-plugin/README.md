# SCS SDK Input Example

[中文](README.zh.md) | **English**

This crate is the safe application-boundary example and real loader fixture for
the SCS Input API 1.00 support in `scs-sdk-crates`. It builds a native plugin for
Euro Truck Simulator 2 or American Truck Simulator without exposing handwritten
application code to raw pointers, C strings, external ABI declarations, or
`unsafe`.

It is intentionally deterministic. The device does not read real hardware and
does not implement networking, a bridge, dispatch logic, persistence, or other
product behavior.

## Public contract demonstrated

The example depends only on `scs-sdk-plugin` and implements `InputPlugin`.
Application code explicitly:

1. declares plugin metadata and Input API compatibility;
2. registers one device during `InputPlugin::initialize`;
3. opts into device activity notifications;
4. handles SCS's per-frame pull requests;
5. returns typed float and bool events with device-local `InputIndex` values;
6. returns `None` when the current event sequence is exhausted; and
7. resets its state during shutdown.

The two Input loader entry points are generated by:

```rust
scs_sdk_plugin::export_input_plugin!(Plugin::default());
```

The finished dynamic library exposes exactly:

```text
scs_input_init
scs_input_shutdown
```

The Input runtime is independent from the Telemetry runtime. A separate plugin
library may expose the Telemetry entry points at the same time, and one `cdylib`
may deliberately invoke both export macros when a product needs both APIs.

## Compatibility contract

The example accepts exactly the currently audited public interface:

| Domain | Requirement |
| --- | --- |
| Input API | 1.00 |
| ETS2 Input game version | 1.00 or a later compatible minor in major 1 |
| ATS Input game version | 1.00 or a later compatible minor in major 1 |
| Architectures | Windows, Linux, and macOS x86-64 plugin processes |

Input API versions, per-game Input versions, Telemetry API versions, Telemetry
schema versions, and public game versions are separate domains. The runtime
validates the Input domains without consulting Telemetry compatibility.

## Device behavior

The plugin registers one generic device named `scs_sdk_input_example` with two
inputs in this exact order:

| Index | Configuration name | Display name | Value type | Behavior |
| ---: | --- | --- | --- | --- |
| 0 | `example_axis` | `Example Axis` | `Float` | Advances from -1.0 to 1.0 by 0.125 every 60 input frames, then resets to -1.0. |
| 1 | `example_button` | `Example Button` | `Bool` | Toggles every 120 input frames. |

The order is part of the device contract. `InputIndex` is local to this device;
it is not interchangeable with a Telemetry SDK index or a device identity.

The example requests activity notifications explicitly. It emits events only
while SCS reports the device as active. When the request contains
`first_in_frame`, the plugin advances its deterministic state and resets the
event cursor. It then returns the axis, the button, and finally `None`, which the
framework maps to the SDK's `NotFound` result for end-of-sequence.

The example retains the official sample's 0.125 step but deliberately extends
its probe across -1.0 to 1.0 so real-game E2E covers negative float values. This
signed sweep is the safe wrapper's normalized axis contract. Application code
must construct an `InputAxisValue` before returning `InputValue::Float`; the
constructor rejects NaN, infinities, and finite values outside -1.0 through 1.0
rather than silently clamping them.

`first_after_activation` is logged as an E2E marker but does not replace
`first_in_frame`; the two flags have distinct meanings in the official API.

## Safe application boundary

From the repository root, run:

```bash
scripts/check-plugin-boundary.sh examples/input-plugin
```

The example uses `#![forbid(unsafe_code)]`. The boundary audit also rejects raw
pointers, handwritten ABI functions, C string types, direct `scs-sdk-sys`
access, and the macro-private `scs_sdk_plugin::__private` path. Necessary FFI,
callback context, panic containment, and lifetime handling remain in the
audited sys, wrapper, and runtime crates.

## Build and verify

Run all commands from the repository root. Each script builds a release dynamic
library and verifies its native format, x86-64 architecture, and exact two
loader exports. The macOS script also ad-hoc signs and verifies the artifact.

### Windows x86-64

```bash
scripts/build-windows-input-plugin.sh
```

Artifact:

```text
target/x86_64-pc-windows-gnu/release/scs_sdk_input_example.dll
```

### Linux x86-64, glibc 2.17 baseline

```bash
scripts/build-linux-input-plugin.sh
```

Artifact:

```text
target/x86_64-unknown-linux-gnu/release/libscs_sdk_input_example.so
```

### macOS x86-64

```bash
scripts/build-macos-input-plugin.sh
```

Artifact:

```text
target/x86_64-apple-darwin/release/libscs_sdk_input_example.dylib
```

The macOS target remains x86-64 on Apple Silicon because the current SCS game
plugin process runs through Rosetta.

## Install and exercise

Exit the game completely before replacing a plugin. On macOS, build and install
the verified private copy with:

```bash
scripts/build-macos-input-plugin.sh
scripts/install-macos-input-plugin.sh
```

The installer preserves the release artifact, removes quarantine from a private
copy, ad-hoc signs it, verifies the exact two Input exports, replaces the exact
generic Input example filename, verifies the installed destination, and then
removes only the exact semantical Input fixture filename. It leaves Telemetry
fixtures and unrelated plugins intact because the two SCS interfaces may
coexist.

For manual installation on another platform, copy the corresponding artifact
into the game's native plugin directory:

| Platform | Plugin directory |
| --- | --- |
| Windows | `<GAME_INSTALL>/bin/win_x64/plugins/` |
| Linux | `<GAME_INSTALL>/bin/linux_x64/plugins/` |
| macOS | `<GAME_APP>/Contents/MacOS/plugins/` |

The generic and semantical Input examples are mutually exclusive installations
because both export the same Input loader interface. Do not keep either fixture
under renamed duplicate filenames. A Telemetry example may remain installed
because it exports a different loader interface.

After startup, check the game's `game.log.txt` for the library load and these
runtime markers:

```text
[scs-sdk-plugin/input] starting plugin name="SCS SDK Input Example" ...
[scs-sdk-plugin/input] detected ... input_api=1.0 input_game_version=1.0
[scs-sdk-input-example] registered generic device with 2 inputs
[scs-sdk-plugin/input] initialized ... devices=1
```

Open the game's input/controller settings and bind or activate the example
inputs so SCS starts polling the device. Activity transitions and the first poll
after activation appear together with one bounded complete event sequence:

```text
[scs-sdk-input-example] device active=true
[scs-sdk-input-example] first poll after activation
[scs-sdk-input-example] emitted index=0 type=float value=...
[scs-sdk-input-example] emitted index=1 type=bool value=...
[scs-sdk-input-example] event sequence exhausted
```

These markers prove that the real game invoked the activity and event
trampolines, exercised both raw union representations, and polled through the
`NotFound` end-of-sequence boundary. They are emitted only once per activation,
so the fixture does not flood `game.log.txt`.

On final game exit, confirm:

```text
[scs-sdk-input-example] shutdown
[scs-sdk-plugin/input] shutdown complete plugin name="SCS SDK Input Example" ...
unloaded 'libscs_sdk_input_example'
```

The release E2E gate requires the complete load, registration, activation,
float, bool, exhaustion, shutdown, and unload sequence from one real game run.
On macOS ETS2, the live log is:

```text
~/Library/Application Support/Euro Truck Simulator 2/game.log.txt
```
